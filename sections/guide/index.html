📖 الملخص التنفيذي الشامل (@mazinjb)

ملخص الدروس ودورة حياة الفريق والإدارة

مرجع مختصر وواضح يشرح: كيف تبدأ دورة حياة العمل من لحظة تكليف المطور بالمهمة، وكيف يعمل كل فريق باستقلالية، وكيف تدير وتعتمد التعديلات خطوة بخطوة.

🔗 مستودع GitHub 📋 طلبات الموافقة (Pull Requests)

🔄 أولاً: دورة الحياة الكاملة (من الفكرة حتى النشر الرسمي)

الخطوة 1 👑 دور الإدارة (المدير)

التكليف وتوزيع الغرف

يحدد المدير مهمة كل مطور ويعطيه صلاحية الدخول للمستودع، مع تحديد المجلد الخاص به فقط (مثلاً: المطور 2 مسؤول عن sections/team/).

الخطوة 2 👨‍💻 دور المطور (الفريق)

إنشاء مسودة والتطوير محلياً

يسحب المطور أحدث نسخة على جهازه، وينشئ فرع مسودة مستقل (Branch)، ثم يبرمج تعديله داخل مجلد قسمه فقط ويختبره على جهازه.

الخطوة 3 👨‍💻 دور المطور (الفريق)

رفع المسودة وطلب الموافقة (PR)

يرفع المطور مسودته إلى GitHub ويفتح طلب دمج (Pull Request). هنا يظهر له القفل الأحمر ولا يستطيع دمج شغله بنفسه أبداً.

الخطوة 4 🤖 دور الروبوت التلقائي

فحص العزل وتجهيز المعاينة

يتأكد الروبوت أن المطور لم يلمس غرف زملائه، ثم ينشر نسخة معاينة مؤقتة (/pr-X/) ويكتب رابطها في تعليق للمدير.

الخطوة 5 👑 دور الإدارة (المدير)

المعاينة واتخاذ القرار

يضغط المدير على رابط المعاينة ويجرب التعديل بالمتصفح: إما أن يوافق (Approve) فيفتح القفل، أو يطلب تعديلاً (Request changes).

الخطوة 6 👑 دور الإدارة (المدير)

الدمج وتحديث الموقع الرسمي

يضغط المدير زر Merge pull request فينتقل التعديل فوراً للموقع الرسمي (main)، ويحذف الروبوت رابط المعاينة المؤقت.

⚖️ ثانياً: الفرق بين دورة حياة "المطور" ودورة حياة "المدير"

👑 دورة عمل المدير (`@mazinjb`) — من المتصفح فقط

  1. استلام الإشعار: يصلك إشعار بوجود Pull Request جديد من أحد المطورين.
  2. تجربة المعاينة: تضغط على رابط المعاينة (Live Preview) الموجود في تعليق الروبوت لتجربة التعديل.
  3. المراجعة (Review): تضغط Files changed ثم الزر الأخضر Submit review:
    • تختار Approve إذا كان العمل ممتازاً.
    • تختار Request changes إذا كان يحتاج إصلاحاً.
  4. النشر النهائي (Merge): تضغط Merge pull request ثم Confirm merge ثم Delete branch.
  5. التراجع عند الطوارئ (Revert): إذا ظهر خطأ بعد النشر، تضغط زر Revert لإلغاء التعديل فوراً.

👨‍💻 دورة عمل المطور (الفريق عن بُعد) — على جهازه

  1. تحديث النسخة: يسحب أحدث نسخة من الموقع الرسمي (git pull origin main).
  2. فتح مسودة جديدة: ينشئ فرعاً باسم مهمته (git checkout -b feat/my-task).
  3. الالتزام بغرفته: يعدل فقط داخل مجلده المخصص (مثلاً sections/team/) ويختبره محلياً.
  4. الرفع لـ GitHub: يحفظ ويرفع المسودة (git push) ويفتح Pull Request.
  5. انتظار قرار المدير: ينتظر مراجعتك؛ فإن طلبت تعديلات يصلحها ويرفعها فتتحدث المعاينة تلقائياً حتى توافق.

🎓 ثالثاً: ملخص الدروس العملية (سجل التدريب خطوة بخطوة)

الدرس الأول ✅ تم تطبيقه

تأسيس المستودع، عزل الغرف، وتفعيل النشر التلقائي (GitHub Pages)

الفكرة المختصرة: بدلاً من أن يعمل المطورون في ملف واحد ويتصادموا، قسمنا الموقع إلى 4 مجلدات معزولة (home, team, services, contact)، وبرمجنا روبوت GitHub Actions ليعرض الموقع الرسمي على الإنترنت تلقائياً عبر الفرع gh-pages.

الدرس الثاني ✅ تم تطبيقه (PR #1)

فهم المسودة (Branch) ورابط المعاينة المؤقت (Live Preview)

الفكرة المختصرة: قام المطور الأول بإنشاء مسودة feat/home-dev1 وإضافة شريط الإحصائيات في الرئيسية. شاهدنا كيف ظل الموقع الرسمي دون تغيير، بينما قام الروبوت ببناء رابط معاينة خاص (/pr-1/) لتجربته قبل الدمج.

الدرس الثالث ✅ تم تطبيقه (PR #2)

قفل الفرع الرئيسي (Branch Protection) واعتماد مطور خارجي (`@mazinprog`)

الفكرة المختصرة: أضفنا حساب المطور الثاني mazinprog وفعلنا القفل على الفرع الرئيسي main مع CODEOWNERS. عندما رفع المطور تعديله في قسم الفريق، ظهر له القفل الأحمر (Merging is blocked)، ولم يُفتح الزر الأخضر إلا بعد دخول المدير mazinjb والضغط على Approve.

الدرس الرابع 🔜 التمرين القادم

رفض التعديل وطلب الإصلاح من المطور (`Request Changes`)

الفكرة المختصرة: ماذا تفعل كمدير إذا فتحت رابط المعاينة لقسم الخدمات (services) ووجدت خطأ أو تصميماً غير مناسب؟ سنتدرب على الضغط على Request changes وكتابة ملاحظة للمطور، وكيف يصلحها المطور وتتحدث المعاينة تلقائياً.

الدرس الخامس 🔜 تمرين متقدم

حماية الغرف من التعدي (`Scope Check`)

الفكرة المختصرة: ماذا يحدث لو حاول مطور قسم التواصل (contact) تعديل ملف في قسم الرئيسية؟ سنتدرب على رؤية كيف يكشفه الروبوت الحارس ويرفض طلبه تلقائياً باللون الأحمر.

الدرس السادس 🔜 خطة التوسع لـ ComeHere

تطبيق النظام على (Frontend + Backend) وتحديثات الموبايل (`EAS OTA`)

الفكرة المختصرة: عزل السيرفر وقاعدة البيانات وصلاحيات الدخول (Roles) في مستودع Backend سري خاص بالمدير، وتطبيق نظام الغرف والمعاينات على مستودع Frontend مع ربطه بباركود المعاينة وتحديثات الهواء (OTA) للجوال.
